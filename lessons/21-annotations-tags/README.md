# บทที่ 21: annotations และ tags 🏫

บทนี้เขียนให้อ่านเองได้ ตัวอย่างทุกอันรันได้จริง ลองรันแล้วแก้ค่าเล่นดูระหว่างอ่าน

## จบบทนี้แล้วทำอะไรได้

- ข้าม test ด้วย `test.skip` (ทั้งแบบข้ามเสมอและแบบมีเงื่อนไข) และ `test.fixme`
- บอกว่า test นี้ "รู้ว่าพัง" ด้วย `test.fail` และเพิ่มเวลาด้วย `test.slow`
- ติด tag เช่น `@smoke` แล้วเลือกรันด้วย `--grep` และ `--grep-invert`
- รู้ว่า `.only` อันตรายอย่างไร และ `forbidOnly` ช่วยอะไร

## เชื่อมกับที่รู้แล้ว

Jest มี `test.skip`, `test.only`, `test.todo`, และ `--testNamePattern` (`-t`) ใน Playwright มีของเหมือนกันและเพิ่มความสามารถ: ข้ามตามเงื่อนไข (เช่นตาม browser), มี `test.fail` ที่ Jest ไม่มี, และมี tag ที่เป็นของจริง (ใน Jest ต้องแอบใส่ใน title เอง) การเลือกรันเฉพาะบางกลุ่มตาม title ที่เคยใช้ `-t` เทียบได้กับ `--grep`

## เนื้อหา

### 1. สรุป annotation

| การเรียก | ผล | ใช้เมื่อ |
|---|---|---|
| `test.skip(...)` | ข้าม (ไม่รัน) | ไม่เกี่ยวข้อง/ไม่รองรับในสภาพแวดล้อมนี้ |
| `test.fixme(...)` | ข้าม และสื่อว่า "ต้องแก้ทีหลัง" | test หรือแอปพังอยู่ รอแก้ |
| `test.fail()` | รันจริง ต้อง fail จึงจะนับว่าผ่าน | บั๊กที่รู้แล้ว อยากให้เตือนเมื่อมีคนแก้ |
| `test.slow()` | เพิ่ม timeout ของ test ขึ้น 3 เท่า | test ที่ช้าตามธรรมชาติ |

แต่ละตัวบันทึกเป็น annotation ใน HTML report (`pnpm report`) ดูย้อนหลังได้ว่าอะไรถูกข้ามด้วยเหตุผลอะไร

### 2. test.skip และ test.fixme

เรียกได้ 3 แบบ

```ts
// (ก) ข้ามทั้ง test เสมอ แทน test(...) ไปเลย
test.skip("ชื่อ test", async ({ page }) => { /* ... */ });

// (ข) ข้ามแบบมีเงื่อนไข เรียกใน test (หรือใน beforeEach)
test("หน้าแรก", async ({ page, browserName }) => {
  test.skip(browserName === "firefox", "ยังไม่รองรับ firefox");
  // ถ้าเงื่อนไขจริง บรรทัดนี้เป็นต้นไปไม่รัน
  await page.goto("/");
});

// (ค) ข้ามทั้งกลุ่ม
test.describe.skip("กลุ่มที่ปิดไว้", () => { /* ... */ });
```

อาร์กิวเมนต์ที่สองคือเหตุผล ควรเขียนทุกครั้งเพื่อให้คนอ่านรายงานเข้าใจ `test.fixme` ใช้เหมือนกันทุกประการ ต่างกันที่ความหมาย: `skip` = ไม่ต้องรันเพราะไม่เกี่ยว, `fixme` = ควรรันแต่ตอนนี้พังอยู่ ต้องแก้ (แบบฝึกหัดของคอร์สนี้ใช้ `test.fixme` เป็น "ข้อที่ยังไม่ได้ทำ" ด้วยเหตุผลเดียวกัน)

`browserName` เป็น fixture มีค่า `"chromium"`, `"firefox"` หรือ `"webkit"` repo นี้รันแค่ chromium ตอนนี้ตัวอย่างจึงไม่ถูกข้ามจริง (เงื่อนไข `browserName === "firefox"` เป็นเท็จ) แต่รูปแบบเดียวกันนี้จะมีประโยชน์เมื่อบท 43 เพิ่มหลาย browser เงื่อนไขอื่นที่ใช้บ่อยได้แก่ `process.env.CI`, `isMobile`, ระบบปฏิบัติการ

### 3. test.fail: รู้ว่าพังแต่ถือว่าผ่าน

```ts
test("หน้าสินค้า p01 แสดงราคา 999 บาท (บั๊กที่รู้แล้ว)", async ({ page }) => {
  test.fail();
  await page.goto("/products/p01");
  await expect(page.getByText("999 บาท")).toBeVisible({ timeout: 1000 });
});
```

- ถ้า test **fail** ตามที่ประกาศไว้ ผลคือ **ผ่าน** (ในรายงานแบบ list จะมีเครื่องหมาย ✘ นำหน้า แต่ท้ายสุดนับเป็น `passed` ไม่ใช่ failed ดูตัวเลขสรุปเป็นหลัก)
- ถ้า test **ผ่าน** โดยไม่คาดคิด (เช่นมีคนแก้บั๊กแล้ว) test จะกลายเป็น **fail** เพื่อเตือนให้ลบ `test.fail()` ออก

ต่างจาก `test.fixme` ตรงที่ยังรันอยู่ทุกครั้ง จึงรู้ทันทีเมื่อสถานะของบั๊กเปลี่ยน ใช้กับบั๊กที่ทีมรับรู้แล้วและมีตั๋วงานรออยู่ ใส่ลิงก์ตั๋วไว้ในชื่อหรือคอมเมนต์

### 4. test.slow

```ts
test("หน้า slow โหลดข้อมูลเสร็จ", async ({ page }) => {
  test.slow(); // timeout ของ test นี้ = 3 เท่าของค่าปกติ (ค่าเริ่มต้น 30 วินาที เป็น 90 วินาที)
  // ...
});
```

ใช้กับ test ที่ช้าจริงตามธรรมชาติ (ขั้นตอนเยอะ หน้าหนัก) ไม่ใช่วิธีซ่อน test ที่ไม่เสถียร ถ้าช้าเพราะต้องรอเวลาเฉยๆ ให้ทบทวนก่อนว่ามีทางที่เร็วกว่าไหม (เช่น mock, บท 33)

### 5. tag: ติดป้ายให้ test

ใส่ใน object อาร์กิวเมนต์ที่สองของ `test` (หรือของ `test.describe`):

```ts
test("หน้าแรกแสดงหัวข้อ DN Shop", { tag: "@smoke" }, async ({ page }) => { /* ... */ });

test("ตะกร้าว่าง", { tag: ["@smoke", "@cart"] }, async ({ page }) => { /* ... */ });

test.describe("ตะกร้า", { tag: "@cart" }, () => { /* ทุก test ในกลุ่มมี @cart */ });
```

- tag ต้องขึ้นต้นด้วย `@`
- ใช้บอกชนิด เช่น `@smoke` (ชุดตรวจเร็วเฉพาะเรื่องสำคัญ), `@cart`, `@slow`
- Playwright เติม tag ต่อท้ายชื่อใน report ด้วย (`หน้าแรกแสดงหัวข้อ DN Shop @smoke`)
- ใน object เดียวกันใส่ `annotation: { type: "issue", description: "https://..." }` เพื่อแนบลิงก์ตั๋วงานเข้า report ได้

### 6. เลือกรันด้วย --grep และ --grep-invert

`--grep` รับ regular expression เทียบกับ **ชื่อเต็มของ test** (ชื่อกลุ่ม + ชื่อ test + tag) เลือกเฉพาะที่ตรง `--grep-invert` ตรงข้าม: รันทุกตัว **ยกเว้น** ที่ตรง

```bash
pnpm test 21-annotations-tags --grep "@smoke"
pnpm test 21-annotations-tags --grep-invert "@smoke"
pnpm test 21-annotations-tags --grep "@smoke|@cart"
pnpm test 21-annotations-tags --grep "@smoke" --grep-invert "@cart"
```

บรรทัดที่ 3 คือ smoke **หรือ** cart บรรทัดที่ 4 คือ smoke **แต่ไม่ใช่** cart (ทดลองรันจริงด้วย Playwright 1.65 ได้ผลตามนี้)

เรื่องการใส่เครื่องหมายคำพูด ใช้ **เครื่องหมายคำพูดคู่ `"..."` ครอบเสมอ** ให้ใช้ได้ทั้ง macOS (zsh) และ Windows PowerShell 5.1 เหตุผลคือ

- `@smoke` ที่ไม่มีเครื่องหมายคำพูดนำหน้า ใน PowerShell `@` ตัวหน้าสุดของอาร์กิวเมนต์มีความหมายพิเศษ (splatting) ต้องครอบด้วยเครื่องหมายคำพูด
- `|` ใน regular expression ถ้าไม่ครอบ shell จะตีความเป็น pipe ใน zsh และ PowerShell
- ไม่ใช้เครื่องหมายคำพูดเดี่ยว `'...'` เพราะ cmd.exe ไม่รู้จัก (pnpm บน Windows ผ่าน cmd ได้)

และเพราะ `--grep` เป็น regex เทียบกับชื่อทั้งหมด ข้อควรระวังคือชื่อ test ที่มีข้อความ `@smoke` อยู่ในชื่อจะตรงด้วย และ `@cart` จะตรงกับ `@cartridge` ถ้าเกิดมี ตั้งชื่อ tag ให้ไม่ซ้อนทับกัน

การรันหนึ่งไฟล์หรือหนึ่ง test ก็ใช้ `--grep` ได้ เช่น `--grep "หน้าแรก"` สำหรับค้นตามชื่อ (ใช้ชื่อภาษาไทยได้)

### 7. test.only และ forbidOnly

```ts
test.only("ฉันรันเดี่ยว", async ({ page }) => { /* ... */ });
```

`.only` ทำให้ Playwright รันเฉพาะ test นั้น (ในรอบที่รันนั้น ไม่ว่าจะอยู่ไฟล์ไหน) เหมาะกับ **ตอนกำลังเขียน test** เพื่อรันเร็วๆ แต่เป็นอันตรายถ้า commit ค้างไว้: test อื่นทั้งหมดไม่ถูกรัน แต่ผลยังเป็น "ผ่าน" ซ้ำร้ายคือไม่มีใครรู้

ป้องกันด้วย `forbidOnly: !!process.env.CI` ใน config (ตั้งไว้แล้วใน `playwright.config.ts` ของ repo นี้) เมื่อรันใน CI ถ้ามี `.only` หลงเหลือ Playwright จะ fail ทันที ไม่ปล่อยผ่าน แต่ปลอดภัยที่สุดคือไม่ commit `.only` เลย ใช้ `--grep` หรือระบุชื่อไฟล์/บรรทัด (`pnpm test 21-annotations-tags --grep "ชื่อ"`) แทนเมื่อต้องการรันเดี่ยว

## จุดที่มักพลาด

- **ลืมเหตุผลใน `skip`/`fixme`**: อีกครึ่งปีไม่มีใครรู้ว่าข้ามทำไม
- **ใช้ `test.fail()` ไม่ใส่ timeout สั้น**: assertion ที่รู้ว่าพังจะรอเต็ม 5 วินาทีทุกรอบ ใส่ `{ timeout: 1000 }`
- **คิดว่า ✘ ของ `test.fail` แปลว่า fail**: ดูบรรทัดสรุปว่า `passed` หรือ `failed` กี่ตัว
- **ลืมครอบ `--grep` ด้วย `"..."`**: `@` ใน PowerShell และ `|` ใน shell ต่างๆ ทำให้คำสั่งพัง
- **commit `.only` ค้าง**: ลบก่อนเสมอ (ในโฟลเดอร์ `solutions` ไม่มี `.only` เหลืออยู่)
- **ใช้ `test.slow()` ซ่อน test ไม่เสถียร**: เป็นการเพิ่ม timeout ไม่ได้แก้สาเหตุ
- **ตั้ง tag ไม่มี `@`**: Playwright ปฏิเสธ tag ที่ไม่ขึ้นต้นด้วย `@`

## วิธีรันบทนี้

```bash
pnpm test 21-annotations-tags
```

ผลที่ควรได้ก่อนเริ่มทำแบบฝึกหัด: `2 passed` และ `5 skipped` (ตัวที่ใช้ `test.fail()` ขึ้นเครื่องหมาย ✘ แต่นับใน passed)

ลองรันเลือกตาม tag ได้ทันทีหลังทำข้อ 1 และ 4:

```bash
pnpm test 21-annotations-tags --grep "@smoke"
pnpm test 21-annotations-tags --grep-invert "@smoke"
```

## แบบฝึกหัดในบทนี้

1. เขียน test ของหน้าสินค้า p03 ติด `@smoke` และใช้ `test.skip` ตามเงื่อนไข `browserName === "webkit"`
2. ใช้ `test.fail()` กับ test ที่คาดผิดจากความจริง (หน้า p02 ราคา "1,000 บาท") แล้วลองลบ `test.fail()` ดูว่ากลายเป็น fail
3. ใช้ `test.slow()` กับ test ที่กดโหลดข้อมูลในหน้า slow
4. ติด tag `@smoke` และ `@cart` ให้ test ตะกร้าว่าง แล้วรันด้วย `--grep "@cart"` และ `--grep-invert "@cart"`
5. ลองใส่ `.only` ให้ test หน้า login รันดูว่ามีตัวเดียวที่รัน แล้ว **ลบ `.only` ออก**
