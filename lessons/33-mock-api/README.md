# บทที่ 33: จำลอง API ด้วย page.route และ route.fulfill

บทนี้เขียนให้อ่านเองได้ ตัวอย่างทุกอันรันได้จริง ลองรันแล้วแก้ค่าเล่นดูระหว่างอ่าน

## จบบทนี้แล้วทำอะไรได้

- ดักคำขอ network ของหน้าเว็บด้วย `page.route` แล้วตอบข้อมูลที่เราสร้างเองด้วย `route.fulfill`
- จำลองสถานการณ์ที่ server จริงทำให้เกิดยาก: รายการว่าง, HTTP 500/503, สินค้าที่ไม่มีใน seed
- รู้ว่าต้องตั้ง route **ก่อน** `goto` และเลือก URL pattern (glob) ให้ตรงคำขอ
- อธิบายได้ว่าทำไมหน้าบางหน้า (เช่น `/products/[id]`) mock ด้วย `page.route` ไม่ได้

## เชื่อมกับที่รู้แล้ว

ใน Jest เรา mock ฟังก์ชันหรือโมดูลที่โค้ดเรียกใช้ (`jest.fn`, `jest.mock`) แล้วกำหนดค่าที่ให้คืนมา ส่วนใน Playwright โค้ดของหน้าเว็บรันอยู่ใน browser เราเข้าไป mock ฟังก์ชันตรงๆ ไม่ได้ แต่เรามี "จุดดัก" ที่เทียบกันได้คือ **ชั้น network**: เมื่อหน้าเว็บเรียก `fetch("/api/products")` Playwright ยื่นมือเข้ามาขวางคำขอนั้นได้ แล้วตอบแทน server ว่าอยากให้ได้อะไร (เหมือน `mockResolvedValue`) หน้าเว็บไม่รู้เลยว่าคำตอบมาจาก test

เหตุผลที่ต้องทำ: บางสถานการณ์เกิดจาก server จริงได้ยากหรือไม่ได้เลย เช่น server ล่ม (500), รายการว่างเปล่า หรือข้อมูลแปลกๆ ที่ seed ไม่มี การ mock ทำให้ test ของหน้าเว็บ (UI) ตรวจพฤติกรรมเหล่านี้ได้ตามต้องการและไม่ต้องพึ่ง server

## เนื้อหา

### 1. page.route: ดักคำขอ

```ts
await page.route("**/api/products*", async (route) => {
  await route.fulfill({ json: { products: [], total: 0 } });
});
await page.goto("/products");
```

- `page.route(pattern, handler)` ลงทะเบียนว่า "ทุกคำขอที่ URL ตรงกับ pattern ให้ส่งเข้า handler ก่อน"
- handler ได้ object `route` มา และ **ต้องจัดการคำขอนั้นให้จบ** ด้วยวิธีใดวิธีหนึ่ง: `route.fulfill(...)` (ตอบเอง), `route.continue()` (ปล่อยไป server จริง), `route.fallback()` (ส่งต่อให้ handler ตัวอื่นที่ตรงกัน), `route.abort()` (ทำให้คำขอล้มเหลว บท 34) ถ้า handler ไม่ทำอะไรเลย คำขอจะไม่ได้คำตอบ เราลองแล้ว หน้า `/products` ค้างที่ "กำลังโหลดสินค้า..." ไม่ไปต่อ
- `route.request()` คือ object ของคำขอที่ถูกดัก (ดู URL, method, body ได้) ใช้ใน handler เมื่ออยากตอบต่างกันตามคำขอ
- `route.fulfill` รับตัวเลือก `status`, `json`, `body`, `contentType`, `headers` (และ `response`, `path` ที่บทหลังๆ ใช้) ถ้าใส่ `json` Playwright แปลงเป็นข้อความและตั้ง `content-type: application/json` ให้ ถ้าไม่ใส่ `status` จะเป็น 200 ถ้าไม่อยากใช้ `json` จะเขียน `body: JSON.stringify(...)` พร้อม `contentType: "application/json"` เองก็ได้

route ที่ตั้งด้วย `page.route` ใช้เฉพาะ page นั้น (ถ้าอยากให้ทุกหน้าใน context ใช้ `context.route` เขียนแบบเดียวกัน) route หายไปเมื่อจบ test เพราะ page ถูกปิด

### 2. ต้องตั้ง route ก่อน goto

นี่คือจุดที่พลาดบ่อยที่สุดของบทนี้ หน้า `/products` เริ่ม `fetch("/api/products")` ทันทีที่โหลดเสร็จ ถ้าเรียก `page.route` หลัง `goto` คำขอแรกอาจไปถึง server จริงไปแล้ว ผลคือหน้าแสดงสินค้าจริง ไม่ใช่ข้อมูลที่ mock

เราลองรันดูแล้ว: เปิด `/products` ก่อน (เห็น "พบสินค้า 10 รายการ") แล้วค่อยตั้ง route ให้ตอบรายการว่าง หน้ายังแสดง 10 รายการเหมือนเดิม handler ไม่ถูกเรียกเลย แต่พอเปลี่ยนหมวดหมู่ใน dropdown (ซึ่งทำให้หน้า fetch อีกครั้ง) คำขอครั้งใหม่นั้นถูก mock ดังนั้น route หลัง goto ใช้ได้กับคำขอที่เกิด "หลังจากนั้น" เท่านั้น ถ้าอยากควบคุมคำขอแรกของหน้า ให้ตั้งก่อน `goto` เสมอ

### 3. URL pattern (glob)

ตัวอย่าง `"**/api/products*"` อ่านว่า:

| ส่วน | ความหมาย |
|---|---|
| `**/` | ข้ามโดเมนและพาธนำหน้าอะไรก็ได้ (จึงไม่ต้องใส่ `http://localhost:3100`) |
| `api/products` | พาธที่ต้องการ |
| `*` ท้ายสุด | ตัวอักษรอะไรก็ได้ ยกเว้น `/` ใช้ครอบคลุม query string (เช่น `?q=...&category=...`) เพราะ URL ที่ใช้เทียบรวม query ด้วย |

เพราะ `*` ไม่ข้าม `/` pattern `"**/api/products*"` จึงตรงกับ `/api/products?q=abc` แต่ไม่ตรงกับ `/api/products/p01` ถ้าอยากให้ตรงทั้งคู่ใช้ `"**/api/products/**"` (สำหรับพาธย่อย) แยกอีก pattern หนึ่งหรือใช้ regular expression ก็ได้ (`/\/api\/products/`) pattern ที่กว้างเกินไปจะดักคำขอที่ไม่ได้ตั้งใจ จึงเขียนให้เฉพาะเจาะจงที่สุดเท่าที่ทำได้

### 4. สามสถานการณ์ที่ mock ช่วยได้

**รายการว่าง** (ตัวอย่างที่ 1): ตอบ `{ products: [], total: 0 }` หน้าแสดง "ไม่พบสินค้าที่ค้นหา" ซึ่งปกติเกิดได้เมื่อค้นหาคำที่ไม่มี แต่การ mock ทำให้ตรวจโดยไม่ต้องหาคำค้นที่ได้ผลว่างพอดี

**HTTP 500** (ตัวอย่างที่ 2): ตอบ `status: 500` หน้าแสดง `role="alert"` "โหลดสินค้าไม่สำเร็จ กรุณาลองใหม่" พร้อมปุ่ม "ลองใหม่" server จริงของเราไม่ล่มตามสั่ง การ mock เป็นทางเดียวที่จะตรวจหน้าจอ error ได้

**สินค้าปลอมที่ไม่มีใน seed** (ข้อ 1): ตอบ product ที่เราแต่งขึ้นเอง ใช้ตรวจว่าหน้าแสดงข้อมูลตามที่ API ให้ ไม่ใช่ข้อมูลที่ฝังไว้ รูปร่างข้อมูลต้องตรงกับ API จริง (`id`, `name`, `category`, `price`, `stock`, `featured`, `description`, `image`) ไม่งั้นหน้าอาจแสดงผิดหรือพัง ดูตัวอย่างจากการเรียก `/api/products` ของจริงเป็นแบบ

### 5. handler ที่มีสถานะ: พังครั้งแรก แล้วปล่อยผ่าน

handler เป็นฟังก์ชันธรรมดา จึงเก็บตัวแปรนอก handler ไว้นับได้ (ข้อ 4):

```ts
let calls = 0;
await page.route("**/api/products*", async (route) => {
  calls += 1;
  if (calls === 1) {
    await route.fulfill({ status: 500, json: { message: "เกิดข้อผิดพลาดภายในระบบ" } });
  } else {
    await route.fallback(); // ไม่ตอบเอง ปล่อยไป server จริง
  }
});
```

คำขอแรกได้ 500 จึงเห็นปุ่ม "ลองใหม่" พอกดปุ่ม หน้าส่งคำขอใหม่ ซึ่งผ่านไป server จริง รายการสินค้าขึ้นตามปกติ นี่คือวิธีจำลอง "พังชั่วคราวแล้วกลับมาดี" (`route.continue()` ก็ปล่อยคำขอไป server เหมือนกัน ต่างกันที่ `continue` ส่งไป network ทันที ไม่ผ่าน handler ตัวอื่น ส่วน `fallback` ให้ handler ตัวถัดไปที่ตรง pattern ได้ทำงานก่อน เมื่อมี handler เดียวสองอย่างนี้ให้ผลเหมือนกัน)

### 6. ทำไมหน้ารายละเอียดสินค้า mock ไม่ได้

ลองตั้ง route ให้ `/api/products/p01` ตอบสินค้าปลอม แล้วเปิด `/products/p01` คุณจะเห็นสินค้าจริงเหมือนเดิม (ข้อ 5) เหตุผล: `page.route` ดัก "คำขอ network ที่ browser ส่งออก" ส่วน `/products/[id]` เป็นหน้าที่ **render ที่ฝั่ง server (SSR)**: server ดึงข้อมูลสินค้าด้วยโค้ดของตัวเอง ประกอบเป็น HTML สำเร็จรูป แล้วส่งมาให้ browser ข้อมูลสินค้าจึงอยู่ใน HTML ที่โหลดมาแล้ว ไม่มี `fetch` จาก browser ให้ดัก (การเรียกจาก server ไปหาข้อมูลเกิดภายใน server เราไม่เห็นและแทรกไม่ได้)

เทียบกับ `/products` (รายการสินค้า) ที่ browser เป็นคน `fetch("/api/products")` เอง เราจึงดักได้ วิธีดูว่าหน้าไหนดักได้: เปิด DevTools แท็บ Network แล้วดูว่ามีคำขอ `fetch/xhr` เรียกข้อมูลหลังโหลดหน้าไหม ถ้าไม่มี (ข้อมูลมากับ HTML) `page.route` ช่วยไม่ได้ ต้องเตรียมข้อมูลฝั่ง server (เช่น เรียก API จริงสร้างข้อมูลไว้ก่อน บท 37) แทน

เรื่องนี้ไม่ใช่ข้อจำกัดของ Playwright แต่เป็นลักษณะของแอปที่ render ฝั่ง server ตอนเขียน test ให้ถามตัวเองก่อนว่า "ข้อมูลนี้มาถึงหน้าทางไหน"

## จุดที่มักพลาด

- **ตั้ง `page.route` หลัง `goto`**: คำขอแรกหลุดไปถึง server จริง (ดูหัวข้อ 2) ตั้งก่อน `goto` เสมอ
- **handler ไม่จบคำขอ**: ลืมเรียก `route.fulfill/continue/fallback/abort` ในบางเงื่อนไข (เช่นเขียน `if` แล้วไม่มี `else`) คำขอนั้นไม่ได้คำตอบ หน้าค้างที่สถานะกำลังโหลด
- **รูปร่างข้อมูลที่ mock ไม่ตรงกับ API จริง**: หน้าแสดงผิดหรือพังแบบงงๆ ดูข้อมูลจริงเป็นต้นแบบเสมอ
- **ลืม `status` เมื่อจำลอง error**: `fulfill({ json: { message: "..." } })` เฉยๆ ได้ status 200 หน้าจึงถือว่าสำเร็จ ต้องใส่ `status: 500` เอง
- **pattern ไม่ตรงคำขอ**: `*` ไม่ข้าม `/` และต้องมี `*` ท้าย pattern ถ้า URL มี query string ถ้า route ไม่ทำงาน ลองพิมพ์ `console.log(route.request().url())` ใน handler หรือเปิด trace (บท 14) ดู URL จริง
- **ดัก pattern กว้างเกินไป** (เช่น `**/api/**`): ดักคำขอที่ไม่ได้ตั้งใจ เช่นคำขอเพิ่มลงตะกร้าด้วย
- **คาดว่า mock ได้ทุกหน้า**: หน้าที่ render ฝั่ง server ไม่มีคำขอให้ดัก
- **`getByRole("alert")` เดี่ยวๆ**: เจอ strict mode violation เพราะ route announcer ของ Next.js (ดูบท 07) ใช้ `.filter({ hasText })`

## หน้าในแอปที่ใช้

**`/products`** (ดึงข้อมูลจากฝั่ง browser): เมื่อโหลดหน้า จะ `fetch("/api/products?...")` แล้วแสดงผลตามสถานะ

| สถานะของ API | สิ่งที่หน้าแสดง |
|---|---|
| กำลังโหลด | `role="status"` "กำลังโหลดสินค้า..." |
| ตอบ 200 มีรายการ | "พบสินค้า N รายการ" และการ์ดสินค้าใน list "รายการสินค้า" |
| ตอบ 200 แต่รายการว่าง | "พบสินค้า 0 รายการ" และ "ไม่พบสินค้าที่ค้นหา" |
| status 400 ขึ้นไป หรือ network error | `role="alert"` "โหลดสินค้าไม่สำเร็จ กรุณาลองใหม่" พร้อมปุ่ม "ลองใหม่" (กดแล้วส่งคำขอใหม่) |

หน้านี้ส่งพารามิเตอร์ `q`, `category`, `sort` ตามที่เลือกในหน้า (ดูได้จาก `route.request().url()`)

**`/products/[id]`** (render ฝั่ง server): ใช้ในข้อ 5 เพื่อพิสูจน์ว่า route ไม่มีผล

```bash
pnpm test 33-mock-api
```

## แบบฝึกหัดในบทนี้

1. จำลองให้ API ตอบสินค้าปลอมที่ไม่มีใน seed หนึ่งชิ้น
2. จำลอง HTTP 503 แล้วตรวจ alert
3. ตอบต่างกันตามคำค้นหา โดยอ่าน query จาก URL ของคำขอ
4. พังครั้งแรก แล้วกด "ลองใหม่" ให้โหลดสำเร็จจาก server จริง (`route.fallback`)
5. พิสูจน์ว่าหน้ารายละเอียดสินค้า (`/products/[id]`) mock ด้วย `page.route` ไม่ได้
