# บทที่ 24: auto-waiting และ actionability 🏫

บทนี้เขียนให้อ่านเองได้ ตัวอย่างทุกอันรันได้จริง ลองรันแล้วแก้ค่าเล่นดูระหว่างอ่าน

## จบบทนี้แล้วทำอะไรได้

- อธิบายได้ว่าทำไม `click()` ถึงไม่ต้องเขียนโค้ดรอเอง และ Playwright ตรวจอะไรบ้างก่อนกด
- รู้ว่า `expect` รอเอง กี่วินาที และเพิ่ม timeout ให้ assertion ที่ช้าจริงได้
- ใช้ `waitForURL` รอการเปลี่ยนหน้าที่เกิดขึ้นทีหลังการกด
- เลิกใช้ `waitForTimeout` (การหยุดรอเวลาตายตัว) ได้อย่างมั่นใจ

## เชื่อมกับที่รู้แล้ว

ใน Jest/Supertest เรา `await` คำสั่งเพื่อรอผลลัพธ์ของ request ครั้งเดียว ใน Playwright เรา `await` ทุกคำสั่งเหมือนกัน (บท 03) แต่หน้าเว็บเปลี่ยนสถานะเองตามเวลา (กำลังโหลด, ปุ่มเพิ่งเปิดใช้งาน, overlay เพิ่งหาย) ถ้าโค้ดทดสอบกดเร็วกว่าหน้า test จะพังแบบสุ่ม Playwright แก้ปัญหานี้ให้โดยรอให้เองในแต่ละคำสั่ง บทนี้อธิบายว่ามันรออย่างไรและเมื่อไรต้องช่วยรอเอง

## เนื้อหา

### 1. auto-waiting คืออะไร

ทุกคำสั่งที่ลงมือกระทำกับ element (`click`, `fill`, `check`, `selectOption`, ...) จะ **ตรวจซ้ำเรื่อยๆ** ว่า element พร้อมให้ทำหรือยัง ถ้ายังไม่พร้อมก็รอ ถ้าพร้อมก็ลงมือทันที ถ้ารอจนหมดเวลาของ test (ค่าเริ่มต้น 30 วินาที) จึงจะ fail พร้อมข้อความบอกว่ารออะไรอยู่

เงื่อนไขที่เรียกรวมกันว่า **actionability** ของ `click()` ต้องผ่านการตรวจ 4 อย่าง คือ Visible, Stable, Receives Events และ Enabled โดยมีข้อกำหนดตั้งต้นว่า element ต้อง Attached (อยู่ในหน้าจริง) ก่อน (ปรับตามชนิดคำสั่ง บางคำสั่งตรวจไม่ครบ ดูตารางในลิงก์ "อ่านเพิ่ม"):

| เงื่อนไข | ความหมาย | ตัวอย่างในหน้า slow |
|---|---|---|
| Attached (ข้อกำหนดตั้งต้น) | element อยู่ในหน้าจริง | ปุ่มถูกวาดแล้ว |
| Visible | มองเห็น (มีขนาด ไม่ซ่อน) | ปุ่มไม่ถูกซ่อนด้วย CSS |
| Stable | ไม่ขยับ (ตำแหน่งนิ่งสองเฟรมติดกัน) | ไม่ได้อยู่ระหว่าง animation |
| Enabled | ไม่ใช่ปุ่ม disabled | ปุ่ม "ส่งฟอร์ม" หลังผ่านไป 1.5 วินาที |
| Receives Events | จุดที่จะกดไม่ถูกอะไรบัง | overlay "กำลังเตรียมหน้า..." |

หน้า `/playground/slow` ถูกออกแบบมาให้เห็นข้อสุดท้ายชัดที่สุด: ใน 1 วินาทีแรก มี overlay "กำลังเตรียมหน้า..." คลุมทั้งหน้า ปุ่ม "โหลดข้อมูล" มองเห็น นิ่ง และ enabled แต่ **กดไม่ได้เพราะโดน overlay บัง** `click()` ตรวจแล้วเห็นว่าจุดที่จะกดเป็นของ overlay ไม่ใช่ของปุ่ม จึงรอและลองใหม่จน overlay หายไปเอง โดยที่โค้ดของเรามีแค่บรรทัดเดียว:

```ts
await page.getByRole("button", { name: "โหลดข้อมูล" }).click();
```

ถ้ารอจนหมดเวลาแล้วปุ่มยังโดนบัง ข้อความ error จะบอกว่า "`<div class="page-overlay">...</div> intercepts pointer events`" แปลว่าตัวนี้เป็นตัวบัง ใช้อ่านหาสาเหตุได้ตรงๆ

### 2. expect ก็รอเอง (web-first assertion)

`expect(locator).toBeVisible()`, `toHaveText(...)`, `toBeEnabled()` ฯลฯ (บท 11–13) ตรวจซ้ำเรื่อยๆ จนผ่านหรือจนหมดเวลา **5 วินาที** เป็นค่าเริ่มต้น ในปุ่ม "โหลดข้อมูล" ที่มี `?delay=1000` ข้อความ "โหลดข้อมูลเสร็จแล้ว" ขึ้นหลังกดไป 1 วินาที `expect` จึงผ่านเอง

ถ้าอาการช้ากว่า 5 วินาทีจริงๆ (เช่น `?delay=7000`) เพิ่ม timeout เฉพาะ assertion ที่ช้า:

```ts
await expect(page.getByRole("status").filter({ hasText: "โหลดข้อมูลเสร็จแล้ว" })).toBeVisible({ timeout: 10_000 });
```

เพิ่มเฉพาะจุดที่รู้ว่าช้า ไม่ต้องเพิ่มทั้งโปรเจกต์ (ไม่งั้นความผิดพลาดจริงจะรายงานช้าลงด้วย)

### 3. waitForURL: รอการเปลี่ยนหน้าที่เกิดทีหลังการกด

บางครั้ง `click()` จบแล้วแต่หน้ายังไม่เปลี่ยน เช่นปุ่ม "ไปหน้าถัดไป" ที่รอ 1 วินาทีก่อนสั่ง `router.push` ตัว `click()` ถือว่างานเสร็จตั้งแต่กดแล้ว (มันไม่รู้ว่าโค้ดของหน้าจะพาไปไหน) ใช้ `waitForURL` รอ URL ใหม่:

```ts
await page.getByRole("button", { name: "ไปหน้าถัดไป" }).click();
await page.waitForURL("**/playground/slow/done");
```

`**/playground/slow/done` เป็น glob: `**` แทนข้อความอะไรก็ได้ (รวมถึง `http://localhost:3100`) จะส่ง regex เช่น `/\/done$/` หรือฟังก์ชันก็ได้ หลัง `waitForURL` ผ่านแล้วค่อยตรวจเนื้อหาของหน้าใหม่ ถ้าไม่ได้ต้องการเน้นที่การรอ `await expect(page).toHaveURL(...)` ก็รอเองได้เหมือนกัน

### 4. ห้าม waitForTimeout

`await page.waitForTimeout(2000)` คือหยุดนิ่ง 2 วินาทีไม่ว่าอะไรจะเกิด ไม่ถูกใจทั้งสองทาง: ถ้าหน้าเสร็จใน 0.3 วินาที เสียเวลาไปเปล่า ถ้าเครื่องช้าและหน้าเสร็จใน 2.5 วินาที test ก็พัง (flaky) Playwright เองก็เตือนไว้ในเอกสารว่าห้ามใช้ในโค้ดจริง ให้เปลี่ยนเป็นการรอ "เหตุการณ์ที่เรารอจริงๆ" เสมอ: `expect(...)` รอข้อความ/สถานะ, `waitForURL` รอ URL, `waitForResponse` รอ request ที่กำลังออกไป (บท 32)

### 5. อย่าตรวจสถานะชั่วคราวที่หายเร็ว

หน้า slow มีสถานะชั่วคราวหลายอย่าง เช่นปุ่มที่ disabled ข้อความ "รอสักครู่..." (ราว 1.5 วินาที) หรือข้อความ "กำลังโหลดสินค้า..." ถ้าเขียน assertion ว่า "ต้องเห็นสถานะนั้น" บนเครื่องที่ช้าหรือกำลังรันหลาย test พร้อมกัน ช่วงเวลานั้นอาจผ่านไปก่อนที่ assertion จะได้ตรวจ test จะ fail แบบสุ่ม (flaky) สถานะชั่วคราวจึงเปราะบาง ให้ตรวจ **สถานะปลายทางที่พลาดไม่ได้** เช่น ปุ่ม "ส่งฟอร์ม" ต้อง enabled, ข้อความ "พบสินค้า 10 รายการ" ต้องขึ้น, ข้อความ "กำลังโหลดสินค้า..." ต้องหายไป (ตรวจ `toBeHidden` หลังเห็นผลลัพธ์ปลายทางแล้ว) ส่วนการ "รอ" ให้ปล่อยให้ auto-waiting ทำ

### 6. แล้ว `networkidle` ล่ะ

`waitForLoadState("networkidle")` รอจนไม่มี request ค้าง Playwright เอกสารไม่แนะนำให้ใช้ในเทสต์ และในแอปนี้ก็ไม่เคยนิ่งจริง อย่าใช้ ให้ `expect` ข้อความหรือ element ที่เราต้องใช้ต่อไปแทน

## จุดที่มักพลาด

- **ใช้ `waitForTimeout` เพราะ test พังบ่อย**: สาเหตุจริงมักเป็น assertion ที่ไม่ใช่ web-first หรือรอผิดเหตุการณ์ หาเหตุการณ์ที่รอจริงแล้วรอสิ่งนั้น
- **คิดว่า `click()` รอการเปลี่ยนหน้าให้**: รอแค่ element พร้อมกด ไม่ได้รอผลที่ตามมา ต้อง `waitForURL` หรือ `expect` ผลนั้นต่อ
- **เพิ่ม timeout ทั้งโปรเจกต์เพราะมี test เดียวช้า**: เพิ่มเฉพาะ assertion นั้น (หรือ `test.slow()` บท 21)
- **ตรวจสถานะชั่วคราวที่หายเร็ว** (เช่น "รอสักครู่..."): เครื่องช้าอาจพลาดช่วงนั้น ตรวจสถานะปลายทางแทน
- **ใช้ `expect(await x.isVisible()).toBe(true)`**: ตรวจครั้งเดียวไม่รอ ใช้ `await expect(x).toBeVisible()` แทน
- **ตรวจก่อนเปลี่ยนหน้า**: หลังกดแล้วไม่ `waitForURL` ทำให้ตรวจเนื้อหาของหน้าเก่า
- **อ่านข้อความ error ไม่ครบ**: ส่วน "Call log" บอกว่ารอเงื่อนไขไหนอยู่ เช่น "element is not enabled" หรือ "intercepts pointer events"

## หน้าในแอปที่ใช้

**`/playground/slow`** อ่าน `?delay=` (ค่าเริ่ม 2000 ms): ปุ่ม "โหลดข้อมูล" แสดง `role="status"` "กำลังโหลด..." แล้วเป็น "โหลดข้อมูลเสร็จแล้ว"; ปุ่ม "ส่งฟอร์ม" ตอนแรก disabled ข้อความ "รอสักครู่..." ประมาณ 1.5 วินาที แล้วเป็น enabled "ส่งฟอร์ม" กดแล้ว "ส่งฟอร์มแล้ว"; overlay "กำลังเตรียมหน้า..." บังหน้า 1 วินาทีแรก; ปุ่ม "ไปหน้าถัดไป" รอ 1 วินาทีแล้วไป `/playground/slow/done` (h1 "เสร็จแล้ว")
**`/products?delay=2000`** แสดง `role="status"` "กำลังโหลดสินค้า..." 2 วินาที แล้วจึงมี "พบสินค้า 10 รายการ"

## วิธีรันบทนี้

```bash
pnpm test 24-auto-waiting
```

ผลที่ควรได้ก่อนเริ่มทำแบบฝึกหัด: `2 passed` และ `4 skipped`

## แบบฝึกหัดในบทนี้

1. โหลดข้อมูลในหน้า slow ด้วย `delay=1500` (เหมือนตัวอย่างที่ 1)
2. รอปุ่ม "ส่งฟอร์ม" จน enabled แล้วกดส่ง
3. หน้าสินค้า `?delay=2000`: เห็น "พบสินค้า 10 รายการ" แล้วข้อความกำลังโหลดต้องหายไป
4. โหลดข้อมูลที่ช้า 7 วินาที ต้องเพิ่ม timeout ของ assertion
