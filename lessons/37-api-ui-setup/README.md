# บทที่ 37: เตรียมข้อมูลผ่าน API แล้วตรวจบนหน้าเว็บ

บทนี้เขียนให้อ่านเองได้ ตัวอย่างทุกอันรันได้จริง ลองรันแล้วแก้ค่าเล่นดูระหว่างอ่าน

## จบบทนี้แล้วทำอะไรได้

- ใช้ `page.request` ส่งคำขอ API ที่ใช้ cookie ชุดเดียวกับหน้าเว็บ
- เตรียมตะกร้า โค้ดส่วนลด คำสั่งซื้อ และการ login ด้วย API แล้ว `goto` ไปตรวจหน้าที่ต้องการทดสอบจริง
- อธิบายได้ว่าทำไมการเตรียมข้อมูลด้วย API เร็วและนิ่งกว่าการคลิกผ่านหน้าเว็บ และเมื่อไหร่ไม่ควรใช้
- แยกความต่างระหว่าง fixture `request` กับ `page.request`

## เชื่อมกับที่รู้แล้ว

บท 36 เรียนใช้ `request` ทดสอบ API ล้วนๆ บท 33-35 เรียนควบคุม network ของหน้าเว็บ บทนี้เอาสองอย่างมาประกอบกัน: ใช้ API เป็น "ทางลัด" สร้างสถานการณ์ แล้วใช้หน้าเว็บตรวจผล ใน Jest เทียบได้กับการเรียกฟังก์ชันสร้างข้อมูลใน `beforeEach` (เช่น `resetUsers()` บท 17 ของ repo ต้นแบบ) แทนที่จะไปทำผ่านขั้นตอนทั้งหมดทุกครั้ง

## เนื้อหา

### 1. ปัญหา: เตรียมข้อมูลผ่านหน้าเว็บช้าและเปราะ

สมมติเราอยากทดสอบหน้า `/cart` ที่แสดงยอดรวมของตะกร้าที่มีสินค้า 3 ชิ้น ถ้าเตรียมผ่านหน้าเว็บ test ต้อง: เปิด `/products` → รอรายการโหลด → หาการ์ดสินค้า → กดปุ่ม → รอข้อความยืนยัน (ทำซ้ำ 3 รอบ) → ไป `/cart` ทั้งที่สิ่งที่เราอยากทดสอบคือ "หน้า cart แสดงยอดถูกไหม" ซึ่งไม่เกี่ยวกับหน้า products เลย

ผลเสียของการเตรียมผ่านหน้าเว็บ:

- **ช้า**: ต้องโหลดหน้า รอ render รอ animation และกดทีละปุ่ม เราลองวัดบนเครื่องนี้ (ตัวเลขขึ้นกับเครื่อง) เพิ่มสินค้า 3 ชิ้นผ่าน API ใช้เวลาราว 15-20 มิลลิวินาที ส่วนผ่านหน้าเว็บ (เปิด `/products` แล้วกดเพิ่มทีละชิ้นรอข้อความยืนยัน) ใช้ราว 300 มิลลิวินาที ต่างกันกว่าสิบเท่า และต่างกันมากขึ้นเมื่อขั้นตอนเตรียมยาวขึ้น
- **เปราะ**: ทุกขั้นตอนที่ผ่านหน้าเว็บเป็นจุดที่พังได้ (locator เปลี่ยน, หน้ายังไม่ hydrate, ปุ่มถูกบัง) ถ้าหน้า products พัง test ของหน้า cart ก็พังตามทั้งที่ cart ไม่ได้ผิด ทำให้หาสาเหตุยาก
- **ซ้ำซ้อน**: หน้า products ควรถูกทดสอบใน test ของมันเอง ไม่ใช่ถูกทดสอบซ้ำทุก test ที่แค่ต้องการมีของในตะกร้า

หลักการ: **เตรียมสิ่งที่ไม่ใช่เป้าหมายของ test ด้วยทางที่เร็วและนิ่งที่สุด (API) แล้วใช้หน้าเว็บเฉพาะส่วนที่เราต้องการตรวจจริง**

### 2. page.request: API ที่ใช้ cookie ร่วมกับหน้าเว็บ

```ts
await page.request.post("/api/cart", { data: { productId: "p01", quantity: 2 } });
await page.goto("/cart");
```

`page.request` คือ `APIRequestContext` (ใช้เหมือน `request` ในบท 36: `get/post/patch/delete`, `data`, `params`) ที่ผูกกับ browser context ของ page ดังนั้น:

- cookie ที่หน้าเว็บมีอยู่จะถูกส่งไปกับคำขอ API
- cookie ที่ server ตั้งใน response ของ API (เช่น `dn_sid` ตอนแรก และ `dn_auth` ตอน login) ถูกเก็บลง browser context ด้วย
- ผลคือ API กับหน้าเว็บเป็น "ผู้ใช้คนเดียวกัน" ใน session เดียวกัน: ตะกร้าที่ API เพิ่มให้ หน้า `/cart` เห็น และ login ด้วย API แล้วเปิด `/account` ได้เลย ไม่ต้องกรอกฟอร์ม `/login`

`page.context().request` ก็คือตัวเดียวกัน ใช้ได้เมื่อมี context แต่ไม่มี page ให้ใช้

### 3. page.request ต่างจาก fixture request อย่างไร

| | fixture `request` (บท 36) | `page.request` |
|---|---|---|
| cookie jar | ของตัวเอง แยกจาก browser | ใช้ร่วมกับหน้าเว็บ (browser context เดียวกัน) |
| ผลต่อหน้าเว็บ | หน้าเว็บมองไม่เห็นสิ่งที่ทำ (คนละ session) | หน้าเว็บเห็นผล (session เดียวกัน) |
| เหมาะกับ | ทดสอบ API ล้วนๆ | เตรียมข้อมูลให้หน้าเว็บ หรือตรวจสถานะหลังทำบนหน้าเว็บ |

เราทดลองในข้อ 5: เพิ่มของด้วย fixture `request` แล้วเปิด `/cart` ด้วย `page` ได้ "ตะกร้าของคุณยังว่างอยู่" เพราะเป็นคนละ session นี่คือจุดที่พลาดบ่อยที่สุดของบทนี้: **ถ้าต้องการให้หน้าเว็บเห็น ต้องใช้ `page.request`**

### 4. ตัวอย่างการเตรียมแบบต่างๆ

**ตะกร้า** (ตัวอย่างที่ 1, ข้อ 1): `POST /api/cart` ด้วย `{ productId, quantity }` ซ้ำตามจำนวนรายการ แล้ว `goto("/cart")`

**โค้ดส่วนลด** (ข้อ 2): `POST /api/cart/coupon` ด้วย `{ code: "DN10" }` โค้ดเก็บใน session ไม่ต้องไปพิมพ์ในช่องบนหน้า

**login** (ตัวอย่างที่ 2): `POST /api/auth/login` ด้วย `{ email, password }` แล้ว cookie `dn_auth` เข้า browser context ทำให้ `goto("/account")` เข้าได้เลย (ถ้าไม่ login จะถูกส่งไป `/login?next=%2Faccount`)

**คำสั่งซื้อ** (ตัวอย่างที่ 2, ข้อ 3): ต้องมีของในตะกร้าก่อน แล้ว `POST /api/orders` ด้วยข้อมูลผู้รับ (`customer: { name, address, phone }`), `shipping` (`"standard"` หรือ `"express"`) และ `payment` (`"card"`, `"transfer"` หรือ `"cod"`) ได้ 201 พร้อมคำสั่งซื้อ (มี `id` เช่น `DN-0001` หมายเลขแยกตาม session) หลังสั่งซื้อ ตะกร้าและโค้ดส่วนลดถูกล้าง (เราลองแล้ว `GET /api/cart` ได้ตะกร้าว่าง `coupon: null`) ผ่านหน้าเว็บต้องไล่ตั้งแต่ `/products`, `/cart`, `/checkout` กรอกฟอร์มและยืนยัน ซึ่งยาวมาก

**สร้างสถานการณ์ที่หน้าเว็บทำยาก** (ข้อ 4): เช่น ทำให้สต็อกเต็มด้วยการเพิ่ม 5 ชิ้นใน request เดียว แล้วตรวจว่าหน้าแจ้ง "สินค้าในสต็อกไม่พอ" เมื่อกดเพิ่มอีก

### 5. ตรวจผลขั้นเตรียมด้วย

ขั้นเตรียมที่พังเงียบๆ ทำให้ test ล้มที่ปลายทางด้วยข้อความที่ไม่บอกต้นเหตุ จึงตรวจ response ของขั้นเตรียมทุกครั้ง:

```ts
const add = await page.request.post("/api/cart", { data: { productId: "p01", quantity: 2 } });
expect(add.status()).toBe(201);   // หรือ await expect(add).toBeOK()
```

หรือใส่ `failOnStatusCode: true` (บท 36) ให้ throw ทันทีถ้าไม่สำเร็จ

### 6. เมื่อไหร่ไม่ควรเตรียมด้วย API

- **เมื่อขั้นตอนนั้นคือสิ่งที่ test นี้ต้องการตรวจ**: test ของการเพิ่มสินค้าลงตะกร้าต้องกดปุ่มบนหน้าจริง (บท 34)
- **ต้องมี test ที่เดินผ่านหน้าเว็บตลอดเส้นทางอย่างน้อยหนึ่งชุด** (เช่น เลือกสินค้า → ตะกร้า → ชำระเงิน) เพื่อยืนยันว่าหน้าเว็บกับ API ทำงานร่วมกันได้จริง การเตรียมด้วย API ใช้กับ test "ที่เหลือ" เพื่อประหยัดเวลา
- API ที่ใช้เตรียมเป็นของ "ภายใน" ที่อาจเปลี่ยน ถ้า API เปลี่ยนรูปแบบ ต้องแก้ทุก test ที่ใช้ (บท 38 เป็นต้นไปจะเรียนวิธีรวบไว้ที่เดียว)

### 7. ลำดับที่ต้องระวัง: หน้าอ่านข้อมูลตอน goto

หน้า `/cart` ดึงข้อมูลตะกร้าตอนโหลดหน้า ถ้า test เปิดหน้าไปแล้วค่อยเพิ่มของทาง API หน้าจะยังแสดงข้อมูลเก่า (เราลองแล้ว: เปิด `/cart` ที่ว่าง เพิ่มของด้วย API แล้วรอ 1.5 วินาที หน้ายังแสดงว่าง ข้อ 5 จึงใช้ `page.reload()`) จึงควร **เตรียมให้เสร็จก่อน `goto`** แล้วไปเปิดหน้า

## จุดที่มักพลาด

- **ใช้ fixture `request` เตรียมข้อมูลให้หน้าเว็บ**: คนละ session หน้าเว็บไม่เห็น ให้ใช้ `page.request`
- **เตรียมหลัง `goto`**: หน้าแสดงข้อมูลเก่า เตรียมก่อนแล้วค่อย `goto` (หรือ `reload`)
- **ลืม `await`**: คำขอ API ไม่ทันเสร็จก่อน `goto` ตะกร้าจึงยังว่างเป็นบางรอบ
- **ไม่ตรวจ status ของขั้นเตรียม**: เช่น เพิ่มสินค้าหมด (409) แล้วไม่รู้ตัว จึงไปพังที่ปลายทางด้วยเรื่องอื่น
- **ลืม login ก่อนเปิดหน้าที่ต้อง login**: `/account` ส่งกลับ `/login?next=%2Faccount`
- **สั่งซื้อโดยตะกร้าว่าง**: `POST /api/orders` ได้ 400 `"ตะกร้าว่าง"` (เราลองสั่งซ้ำหลังตะกร้าถูกล้างแล้วได้ตามนี้) ต้องเพิ่มของก่อน
- **เดาหมายเลขคำสั่งซื้อผิด**: หมายเลขนับต่อ session ถ้าไม่แน่ใจ ให้อ่านจาก response (`(await res.json()).id`)
- **ใช้ API เตรียมแล้วไม่มี test ที่เดินผ่านหน้าเว็บเลย**: เสี่ยงที่หน้าเว็บกับ API ไม่เข้ากันแล้วไม่มีใครรู้
- **ผูก test กับค่าที่แสดงซึ่งไม่ใช่เป้าหมาย**: เช่น ตรวจยอดเงินในประวัติคำสั่งซื้อใน test ที่ตั้งใจตรวจแค่ว่ามีคำสั่งซื้อ

## หน้าในแอปที่ใช้

**`/cart`** (ตะกร้าสินค้า): `<ul aria-label="สินค้าในตะกร้า">` แต่ละ `<li>` คือสินค้าหนึ่งรายการ (ชื่อ ราคา จำนวน ยอดรายการ ปุ่มลบ) ตัวเลขสรุปอยู่ใน `data-testid` `subtotal`, `discount`, `total` ค่าแสดงเป็น "970 บาท" ตะกร้าว่างแสดง "ตะกร้าของคุณยังว่างอยู่"

**`/account`** (ต้อง login): `<h2>` "ประวัติคำสั่งซื้อ" และรายการ `<ul aria-label="ประวัติคำสั่งซื้อ">` แต่ละรายการมีลิงก์หมายเลขคำสั่งซื้อ (เช่น `DN-0001`) ไปหน้ารายละเอียด ถ้ายังไม่มีคำสั่งซื้อแสดง "ยังไม่มีคำสั่งซื้อ"

**`/orders/DN-0001`** (รายละเอียดคำสั่งซื้อ): h1 "สั่งซื้อสำเร็จ", "หมายเลขคำสั่งซื้อ: DN-0001", รายการสินค้า, "ค่าจัดส่ง: N บาท", "ยอดสุทธิ: N บาท" (รวมค่าจัดส่งแล้ว)

**`/products`**: ใช้ในข้อ 4 (การ์ดสินค้าขึ้นหลังหน้าดึงรายการเสร็จ จึงใช้เป็นสัญญาณว่าหน้าพร้อมกดได้) เมื่อเพิ่มลงตะกร้าไม่สำเร็จ แสดงข้อความของ server ใน `role="alert"`

API ที่ใช้: `POST /api/cart`, `POST /api/cart/coupon`, `POST /api/orders`, `POST /api/auth/login` (รายละเอียดในบท 36) บัญชีทดสอบ `user@dnshop.test` / `password123`

## แบบฝึกหัดในบทนี้

1. เตรียมตะกร้าสองรายการด้วย API แล้วตรวจยอดรวมที่ `/cart`
2. เตรียมโค้ดส่วนลด DN10 ด้วย API แล้วตรวจยอดหลังหักส่วนลด
3. สร้างคำสั่งซื้อส่งด่วนพร้อมส่วนลดด้วย API แล้วตรวจหน้ารายละเอียดคำสั่งซื้อ
4. เติมสต็อกในตะกร้าด้วย API แล้วตรวจว่ากดเพิ่มบนหน้าจะแจ้งสต็อกไม่พอ
5. พิสูจน์ว่า fixture `request` กับ `page.request` ใช้ cookie คนละชุด
