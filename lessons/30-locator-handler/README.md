# บทที่ 30: ป๊อปอัปที่โผล่ไม่แน่นอน (addLocatorHandler)

บทนี้เขียนให้อ่านเองได้ ตัวอย่างทุกอันรันได้จริง ลองรันแล้วแก้ค่าเล่นดูระหว่างอ่าน

## จบบทนี้แล้วทำอะไรได้

- อธิบายได้ว่าทำไมแบนเนอร์/ป๊อปอัปที่โผล่ไม่แน่นอนทำให้ test พังแบบสุ่ม
- ใช้ `page.addLocatorHandler` ปิดป๊อปอัปให้อัตโนมัติ โดยไม่ต้องใส่โค้ดเช็คทุกบรรทัด
- รู้ว่า handler ทำงาน "เมื่อไหร่" (ตอนมี action หรือ assertion) และไม่ทำงานเมื่อไหร่
- ใช้ตัวเลือก `times`, `noWaitAfter` และ `page.removeLocatorHandler`

## เชื่อมกับที่รู้แล้ว

บท 24 สอนว่า `click()` รอให้ปุ่มพร้อมเองรวมถึงรอให้ "ไม่ถูกอะไรบัง" (เงื่อนไข receives events) เช่น overlay ที่หายไปเอง แต่ป๊อปอัปบางแบบไม่หายเอง ต้องมีคนกดปิด และโผล่ตอนไหนก็ไม่รู้ (สุ่ม) เช่น แบนเนอร์คุกกี้ ป๊อปอัปโปรโมชัน ใน Jest/Supertest ไม่มีปัญหานี้ เพราะไม่มีหน้าจอ บทนี้สอนวิธีสอน Playwright ว่า "ถ้าเห็นสิ่งนี้ ให้ทำแบบนี้ก่อน แล้วค่อยทำต่อ"

## เนื้อหา

### 1. ปัญหา: ป๊อปอัปที่โผล่ไม่แน่นอน

แอปนี้ปิดแบนเนอร์ไว้เป็นค่าเริ่มต้น เปิดได้ด้วย query string:

| URL | สิ่งที่โผล่ | ปุ่มที่ปิดได้ |
|---|---|---|
| `/?cookieBanner=1` | dialog "การใช้คุกกี้" | "ยอมรับทั้งหมด", "ปฏิเสธ" |
| `/?promo=1` | dialog "โปรโมชันพิเศษ" (ข้อความ "ใช้โค้ด DN10 ลด 10%") | "ปิด" |

ใส่ `?cookieBanner=1` หรือ `?promo=1` ที่หน้าไหนก็ได้ (แอปจำค่าไว้ใน cookie ใช้กับทุกหน้าที่เปิดต่อใน context เดียวกัน) แล้วมันจะโผล่ **หลังโหลดหน้า 0.5-2.5 วินาที (สุ่ม)** เป็น modal ที่

- บังการคลิกทุกอย่างในหน้า (เนื้อหาอื่นถูกทำให้ inert)
- ไม่ปิดเมื่อกด `Escape` ต้องกดปุ่มของมันเท่านั้น
- เมื่อปิดแล้วไม่โผล่อีกใน context นั้น (browser context ต่อ test มีของตัวเอง)

ลองทำ flow ยาวๆ เช่น หน้าแรก > สินค้า > เพิ่มลงตะกร้า > ตะกร้า ผลคือ **ผ่านบ้าง พังบ้าง** ขึ้นกับว่าแบนเนอร์โผล่ตอนไหน: ถ้า flow เสร็จก่อนแบนเนอร์โผล่ ก็ผ่านโดยบังเอิญ ถ้าแบนเนอร์โผล่กลางทาง การคลิกถัดไปจะถูกบัง รอแล้วรออีกจนหมดเวลา (ดูตัวอย่างที่ 3 ในไฟล์ spec ซึ่งตั้งเป็น `test.fixme` ไว้เพื่อให้ชุด test ไม่แดงแบบสุ่ม)

### 2. addLocatorHandler: บอกว่า "ถ้าเห็นสิ่งนี้ ให้ทำสิ่งนี้"

```ts
await page.addLocatorHandler(page.getByRole("dialog", { name: "การใช้คุกกี้" }), async (dialog) => {
  await dialog.getByRole("button", { name: "ปฏิเสธ" }).click();
});
```

- อาร์กิวเมนต์แรก: locator ของสิ่งที่เป็นตัวปัญหา (หาด้วย `getByRole` ได้ตามปกติ)
- อาร์กิวเมนต์ที่สอง: ฟังก์ชันที่ "กำจัด" มัน ได้รับ locator ตัวเดียวกันเป็นพารามิเตอร์ (`dialog` ด้านบน) ใช้หาปุ่มข้างในต่อได้
- เรียก **ครั้งเดียวต้นเทส ก่อนเริ่ม flow** (ก่อน `goto` ก็ได้) หลังจากนั้นเขียน test ตามปกติ ไม่ต้องใส่โค้ดรู้เรื่องแบนเนอร์ที่ไหนอีก handler ยังอยู่ตลอดจนจบ test แม้เปลี่ยนหน้าไปมา (ผูกกับ `page` ไม่ใช่หน้าเว็บ)

### 3. handler ทำงานเมื่อไหร่ (สำคัญมาก)

Playwright เรียก handler ตอนที่ **กำลังทำ action หรือ assertion** แล้วเห็นว่า locator ของ handler มองเห็นอยู่ ลำดับคือ

1. ตอนทำ action (`click`, `fill`, `hover` ...) ที่มี actionability check และตอนรอใน `expect(...)` ที่รอเอง Playwright ตรวจก่อนทำ/ก่อนลองใหม่ทุกครั้งว่ามี locator ของ handler โผล่หรือไม่
2. ถ้าโผล่ -> หยุดทำ action นั้น -> รัน handler -> รอให้ locator นั้นหายไป -> ทำ action ต่อ

โยงกับบท 24: `click` รอเงื่อนไข "receives events" (ไม่ถูกบัง) ถ้า modal บังอยู่ การคลิกจะลองซ้ำเรื่อยๆ **ในแต่ละรอบที่ลองซ้ำ Playwright เช็ค handler ก่อน** พอ handler ปิด modal การคลิกก็ผ่านตามปกติ ถ้าไม่มี handler ก็รอจนหมดเวลา

ข้อควรรู้จากเอกสาร (และจากที่ลองรันจริง ตอนรันจะเห็นในรายงานว่า `intercepting action to run the handler`):

- **ถ้าไม่มี action หรือ assertion เลย handler จะไม่ทำงาน**: ถ้าแบนเนอร์โผล่ตอนที่ test ไม่ได้ทำอะไรกับหน้า (เช่น กำลังรอ `goto`) handler ยังไม่ทำงาน มันทำงานตอน action/assertion ถัดไป
- **assertion ที่รอเองก็ทำให้ handler ทำงานด้วย**: เช่น `await expect(dialog).toBeVisible()` ในขณะมี handler ของ dialog เดียวกัน handler จะปิด dialog ก่อน แล้ว assertion จึงล้มเหลว (เพราะ dialog หายไปแล้ว) อย่าใช้ท่านี้ถ้ามี handler ของ dialog นั้นอยู่
- **เวลาที่ handler ใช้นับรวมกับ timeout ของ action/assertion นั้น**: handler ที่ช้ามากทำให้ action หมดเวลาได้
- **handler เปลี่ยนสถานะของหน้ากลาง test**: เช่น โฟกัสย้าย เมาส์ขยับ ให้ใช้ action ที่ทำจบในตัว (เช่น `locator.press("Enter")` แทน `focus()` แล้ว `keyboard.press`) เพราะ handler อาจแทรกระหว่างสองคำสั่ง
- ลงทะเบียนได้หลาย handler (ข้อ 2 ในแบบฝึกหัด) แต่รันทีละตัว และ handler ไม่ควรพึ่งการทำงานของ handler อื่น

### 4. เมื่อไหร่ไม่ควรใช้ handler

เอกสารแนะนำว่า **ถ้าป๊อปอัปโผล่แน่นอนและเรารู้จังหวะ** ให้รอแล้วกดปิดใน flow ปกติของ test ไปเลย (ชัดกว่า) เช่น หน้า login ที่มี dialog ทุกครั้ง ใช้ handler กับสิ่งที่ **โผล่ไม่แน่นอน** (สุ่มเวลา สุ่มว่าจะโผล่หรือไม่ หรือโผล่จากบริการภายนอกที่เราคุมไม่ได้) เท่านั้น

อีกวิธีของฝั่งแอปคือ ใน environment ทดสอบให้ปิดแบนเนอร์เลย (ตั้ง cookie ไว้ก่อน) บทนี้ไม่ทำแบบนั้นเพราะต้องการฝึก handler

### 5. ตัวเลือก times และ noWaitAfter

```ts
await page.addLocatorHandler(locator, handler, { times: 1 });
await page.addLocatorHandler(locator, handler, { noWaitAfter: true });
```

- **`times: n`**: ทำงานได้สูงสุด n ครั้งแล้วถอดตัวเองออก (ค่าเริ่มต้น: ไม่จำกัด) ใช้เมื่อป๊อปอัปโผล่ได้ครั้งเดียว
- **`noWaitAfter: true`**: หลังรัน handler ปกติ Playwright **รอให้ locator นั้นหายไป** (เพื่อให้แน่ใจว่าปิดสำเร็จ) ตัวเลือกนี้ปิดการรอนั้น ใช้เมื่อ locator ไม่ได้หายไปหลัง handler เช่น handler ที่แค่นับจำนวนหรือแค่เรียกฟังก์ชันบนหน้า โดย locator เป็นของที่มองเห็นตลอด (เช่น `h1`) ถ้าลืม `noWaitAfter` Playwright จะรอให้หัวข้อหายไป ซึ่งไม่มีวันเกิดขึ้น แล้ว action นั้นหมดเวลา (ดูแบบฝึกหัดข้อ 5)

### 6. ถอด handler: removeLocatorHandler

```ts
const dialog = page.getByRole("dialog", { name: "การใช้คุกกี้" });
await page.addLocatorHandler(dialog, async () => { /* ... */ });
// ...
await page.removeLocatorHandler(dialog); // ส่ง locator ตัวเดิมที่ใช้ตอนลงทะเบียน
```

ใช้เมื่อช่วงหนึ่งของ test ต้องการให้ป๊อปอัปอยู่ เช่น จะตรวจเนื้อหาของแบนเนอร์เอง ถอดแล้ว Playwright จะไม่ปิดให้อีก (แบนเนอร์จะบังการคลิกเหมือนไม่มี handler)

## จุดที่มักพลาด

- **ลงทะเบียน handler ทีหลัง action ที่โดนบัง**: ต้องลงทะเบียนก่อนเริ่ม flow
- **รอแบนเนอร์ด้วย `expect(dialog).toBeVisible()` ขณะมี handler ของมัน**: handler ปิด dialog ให้ก่อน assertion จึงล้มเหลว
- **handler ไม่ปิดจริง**: ถ้า handler กดปุ่มผิด dialog ยังอยู่ Playwright จะรอให้หายจนหมดเวลา ให้เช็คปุ่มที่กดว่าปิดได้จริง
- **ใช้ handler กับป๊อปอัปที่โผล่แน่นอน**: เขียนปิดตรงๆ ใน flow อ่านง่ายกว่า
- **ใช้ `Escape` ปิดป๊อปอัปของบทนี้**: ไม่ได้ผล (แอปตั้งใจให้ไม่ปิดด้วย Escape) ต้องกดปุ่ม
- **ทำ test ที่เช็คจำนวนครั้งของ handler ด้วย `toBe(1)` ทั้งที่แบนเนอร์อาจยังไม่โผล่**: flow เร็วอาจจบก่อนแบนเนอร์โผล่ ตัวนับจึงเป็น 0 หรือ 1 ตรวจ `toBeLessThanOrEqual(1)` แทน (ดูข้อ 3)

## หน้าในแอปที่ใช้

**`/?cookieBanner=1`** หน้าแรก มีลิงก์ "ดูสินค้าทั้งหมด" และแบนเนอร์ "การใช้คุกกี้" โผล่หลัง 0.5-2.5 วินาที
**`/products?cookieBanner=1`** หรือ **`?promo=1`** ใช้กับทุกหน้าได้ หน้าสินค้ามีปุ่ม "เพิ่มลงตะกร้า"
**`/cart`** h1 "ตะกร้าสินค้า" และรายการ "สินค้าในตะกร้า"

## วิธีรันบทนี้

```bash
pnpm test 30-locator-handler
```

ผลที่ควรได้ก่อนเริ่มทำแบบฝึกหัด: `2 passed` และ `6 skipped` (ตัวอย่างที่ 3 ที่เป็น `test.fixme` ก็นับเป็น skipped)

เมื่อทำแบบฝึกหัดครบแล้วให้ลองรันซ้ำหลายรอบ เพื่อดูว่าไม่มีรอบไหนพัง (ซึ่งเป็นจุดประสงค์ของ handler):

```bash
pnpm test 30-locator-handler --repeat-each=10
```

## แบบฝึกหัดในบทนี้

1. ใช้ handler ปิดแบนเนอร์คุกกี้ โดยเริ่ม flow ที่หน้าสินค้า
2. เปิดแบนเนอร์คุกกี้และโปรโมชันพร้อมกัน ใช้ handler 2 ตัว
3. นับจำนวนครั้งที่ handler ทำงาน (ไม่เกิน 1)
4. ถอด handler ด้วย `removeLocatorHandler` แล้วดูแบนเนอร์บังการคลิก
5. ใช้ `times` และ `noWaitAfter` กับ handler บน element ที่ไม่หายไป
