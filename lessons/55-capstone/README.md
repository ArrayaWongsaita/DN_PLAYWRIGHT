# บทที่ 55: โปรเจกต์ปิดท้าย เขียน test ทั้งเส้นทางการซื้อของ

บทนี้เขียนให้ทำเองได้ ต่างจากบทอื่น: ไม่มีตัวอย่างสำเร็จรูป และไม่มีวิธีทำทีละขั้น ที่ให้มีเพียง **requirement เป็นข้อๆ** กับโครงไฟล์เปล่า คุณออกแบบ Page Object, fixture และตัวช่วยเตรียมข้อมูลเอง โดยใช้สิ่งที่เรียนมาจากบทก่อนหน้า (ส่วนใหญ่คือบท 37 ถึง 41) เมื่อติดให้เปิดบทที่อ้างถึงกลับไปอ่าน

## จบบทนี้แล้วทำอะไรได้

- วางโครงโปรเจกต์ test ของเว็บจริงหนึ่งเว็บ: Page Object ต่อหนึ่งหน้า, fixture ที่ส่ง Page Object ให้ test, ตัวช่วยเตรียมข้อมูลผ่าน API
- login ครั้งเดียวด้วย project `setup` และ `storageState` แล้วให้ทุก test เริ่มด้วยสถานะที่ login แล้ว
- เขียน test ที่เดินครบเส้นทาง ค้นหา เพิ่มสินค้า ใช้คูปอง จ่ายด้วยบัตรใน iframe ดาวน์โหลดใบเสร็จ และดูประวัติคำสั่งซื้อ
- เลือกได้ว่าขั้นไหนควรทำผ่านหน้าเว็บ ขั้นไหนควรเตรียมผ่าน API

## เชื่อมกับที่รู้แล้ว

บทนี้รวมหลายบทเข้าด้วยกัน:

- บท 16 ถึง 17 และ 24: locator และการรอ
- บท 27 และ 29: ดาวน์โหลดไฟล์ และ iframe (ฟอร์มบัตร)
- บท 37: เตรียมข้อมูลผ่าน API ด้วย `page.request` แล้วค่อยตรวจบนหน้าเว็บ
- บท 38 ถึง 40: Page Object และ fixture
- บท 41: `storageState` และ project `setup`

ใน Jest + Supertest ที่เคยทำ งานแบบนี้คือการทำ integration test ที่ครอบทั้งระบบ เพียงแต่ที่นี่ผู้ใช้คือ browser

## เนื้อหา

### 1. โจทย์

ลูกค้าชื่อสมชาย (`user@dnshop.test`) เข้าร้าน DN Shop ค้นหาหนังสือ ใส่ตะกร้าสองเล่ม ใช้โค้ดส่วนลด จ่ายด้วยบัตรเครดิต ดาวน์โหลดใบเสร็จ แล้วเข้าไปดูว่าคำสั่งซื้อขึ้นในบัญชีของเขา งานของคุณคือเขียน test ที่ตรวจแต่ละช่วงของเส้นทางนี้ และอีก test หนึ่งที่เดินทั้งเส้นทางต่อกัน

### 2. Requirement

ต้องมี test ที่ผ่านครบทุกข้อ (หมายเลขข้อใน requirement ไม่ใช่เลขเดียวกับข้อในไฟล์ spec ตารางด้านล่างบอกว่าแต่ละข้ออยู่ที่ใด):

| Requirement | ต้องทำได้ | อยู่ที่ |
|---|---|---|
| 1. login | ทุก test เริ่มด้วยสถานะที่ login แล้ว โดยไม่มีโค้ด login ในตัว test | `auth.setup.ts` และ `shopping-flow.spec.ts` ข้อ 1 |
| 2. ค้นหา | ค้นหา "หนังสือ" แล้วพบ 2 รายการ | `shopping-flow.spec.ts` ข้อ 2 |
| 3. เพิ่มหลายชิ้น | เพิ่มหนังสือสองเล่มจากหน้าสินค้า ตะกร้ามี 2 รายการ ยอดรวม 840 บาท | `shopping-flow.spec.ts` ข้อ 3 |
| 4. คูปอง | ใช้โค้ด DN10 ลด 84 บาท ยอดสุทธิ 756 บาท | `shopping-flow.spec.ts` ข้อ 4 |
| 5. ชำระเงินด้วยบัตร | กรอกบัตรในฟอร์มที่อยู่ใน iframe แล้วสั่งซื้อสำเร็จ | `shopping-flow.spec.ts` ข้อ 5 |
| 6. ดาวน์โหลดใบเสร็จ | ได้ไฟล์ `receipt-DN-0001.txt` ที่เนื้อหาถูกต้อง | `shopping-flow.spec.ts` ข้อ 6 |
| 7. ประวัติคำสั่งซื้อ | คำสั่งซื้อที่สั่งแล้วแสดงในหน้า `/account` | `account.spec.ts` ข้อ 8 ถึง 9 |
| เส้นทางเต็ม | เดินข้อ 2 ถึง 7 ต่อกันด้วย UI ใน test เดียว | `shopping-flow.spec.ts` ข้อ 7 |

ข้อกำหนดของงาน:

- locator ของแต่ละหน้าอยู่ใน Page Object ตัว test ควรอ่านเหมือนประโยคบอกว่า "ทำอะไร ตรวจอะไร"
- ข้อที่ไม่ได้ทดสอบหน้าตะกร้าหรือหน้าชำระเงินเอง ให้เตรียมข้อมูลผ่าน API (ข้อ 4 ถึง 6 และข้อ 9 ในไฟล์ spec) ข้อ 3 และข้อ 7 ใช้ UI ตามที่โจทย์ระบุ
- ห้ามใช้ `waitForTimeout` และห้ามเขียน locator แบบ CSS หรือ XPath ให้ใช้ locator แบบที่เรียนมา (`getByRole`, `getByLabel`, `getByTestId` ฯลฯ)
- test ทุกข้อต้องรันขนานกันได้ และไม่พึ่งลำดับหรือผลของ test อื่น

### 3. โครงไฟล์ที่ให้

```
lessons/55-capstone/
  playwright.config.ts          config ของบทนี้ (เขียนเสร็จให้แล้ว รูปแบบเดียวกับบท 41)
  auth.setup.ts                 โครงของไฟล์ setup (ต้องเขียน)
  fixtures.ts                   โครงของไฟล์ fixture (ต้องเขียน)
  pages/                        โฟลเดอร์ว่างสำหรับ Page Object ของคุณ
  shopping-flow.spec.ts         ข้อ 1 ถึง 7 (test.fixme)
  account.spec.ts               ข้อ 8 ถึง 9 (test.fixme)
  .auth/user.json               ไฟล์สถานะ (สร้างตอนรัน ไม่ถูก commit)
```

ไฟล์ spec ทั้งสองไฟล์ import `test` จาก `./fixtures` ตั้งแต่แรก เมื่อคุณเพิ่ม fixture ใน `fixtures.ts` ก็ขอใช้ใน argument ของ test ได้ทันที

### 4. ข้อแนะนำการออกแบบ

**ลำดับที่ทำง่ายที่สุด**

1. เขียน `auth.setup.ts` ให้ผ่านก่อน (ข้อ 1) ดูรูปแบบจาก `lessons/41-auth-storage-state/auth.setup.ts` อย่าลืมลบ cookie `dn_sid` ก่อนบันทึกสถานะ มิฉะนั้นทุก test จะใช้ตะกร้าและคำสั่งซื้อร่วมกัน (เหตุผลอยู่ในบท 41 หัวข้อ 5)
2. เขียน Page Object ทีละหน้าตามที่ข้อนั้นต้องใช้ ใส่ไว้ใน `pages/` เริ่มจาก `/products` (ข้อ 2 และ 3) แล้วหน้าตะกร้า หน้าชำระเงิน หน้าคำสั่งซื้อ และหน้าบัญชี
3. เขียนตัวช่วยเตรียมข้อมูลผ่าน API แล้วทำเป็น fixture
4. เขียน test ข้อ 4 ถึง 9 แล้วจบที่ข้อ 7 (เส้นทางเต็ม) ซึ่งเป็นการประกอบทุกอย่างที่ทำมา

**Page Object**

เก็บ locator และ method ที่เป็น "การกระทำ" ของหน้านั้น เช่น `search(term)`, `applyCoupon(code)` ส่วน `expect` ที่ตัดสินว่า test ผ่านหรือไม่ให้เขียนใน test โดย Page Object คืน locator ให้ test เอาไปตรวจ (เหตุผลอยู่ในบท 38)

**fixture และข้อมูลที่เตรียมผ่าน API**

ตัวช่วยเตรียมข้อมูลคือคลาสหรือฟังก์ชันที่เรียก API ด้วย `page.request` (ใช้ cookie ชุดเดียวกับหน้าเว็บ บท 37) แล้วห่อเป็น fixture API ของแอปที่ใช้ได้ในบทนี้:

| ทำอะไร | คำสั่ง |
|---|---|
| ใส่สินค้าลงตะกร้า | `POST /api/cart` body `{ "productId": "p08", "quantity": 1 }` ตอบ 201 |
| สั่งซื้อ | `POST /api/orders` body `{ "customer": { "name": "...", "address": "...", "phone": "0812345678" }, "shipping": "standard", "payment": "cod" }` ตอบ 201 (ตะกร้าต้องมีของ) |

ตรวจ status ของคำสั่งเหล่านี้ทุกครั้ง ถ้าเตรียมข้อมูลไม่สำเร็จแล้วปล่อยผ่าน test จะล้มที่ขั้นหลังๆ ด้วยข้อความที่ไม่บอกต้นเหตุ

**ทำไมข้อมูลของแต่ละ test ไม่ชนกัน**

เพราะ `auth.setup.ts` ลบ `dn_sid` ออกจากไฟล์สถานะ แต่ละ test จึงได้ session ใหม่ ตะกร้าว่าง ไม่มีคำสั่งซื้อ และคำสั่งซื้อแรกมีหมายเลข `DN-0001` เสมอ (ใช้ค่านี้ในผลที่คาดหวังได้)

### 5. การทำให้ test นิ่ง

ปัญหาสองอย่างที่พบในบทก่อนๆ เกิดได้ในโปรเจกต์นี้ด้วย:

- **กดปุ่มซ้ำเร็วเกินไป**: ปุ่ม "เพิ่มจำนวน" ที่ `/cart` คำนวณจากค่าที่หน้าแสดงอยู่ตอนนั้น ถ้ากดซ้ำก่อนที่หน้าจะแสดงค่าใหม่ จะได้จำนวนน้อยกว่าที่ตั้งใจ (อธิบายไว้ในบท 12 และ 38) ให้ method ของ Page Object รอผลของการกดแต่ละครั้งก่อนจบ method เช่นรอค่าจำนวนใหม่ด้วย `toHaveValue` และปุ่ม "เพิ่มลงตะกร้า" ที่ `/products` ก็ให้รอข้อความสถานะของสินค้าชิ้นนั้นก่อนกดชิ้นถัดไป
- **หน้ายังไม่ hydrate**: หน้า `/checkout`, `/cart` และฟอร์มใน iframe เป็นหน้าที่ React ต้องทำงานก่อนฟอร์มจึงรับค่า ถ้ากรอกเร็วเกินอาจถูกล้างค่า (อธิบายไว้ในบท 29 หัวข้อ 7) `page.goto` รอถึง event `load` ให้อยู่แล้ว และให้ตรวจค่าในช่องหลัง `fill` เพื่อให้เห็นปัญหาตั้งแต่ขั้นนั้น

ข้อห้ามคือแก้ด้วยการหน่วงเวลา ให้รอสิ่งที่เห็นบนหน้าเสมอ

### 6. รายละเอียดที่ต้องใช้

**ฟอร์มบัตร (ข้อ 5)** อยู่ใน `<iframe title="ฟอร์มบัตรเครดิต">` ที่ปรากฏเมื่อเลือกวิธีชำระเงินเป็นบัตรเครดิต เลขบัตรที่ผ่านคือ `4242 4242 4242 4242` ช่อง "วันหมดอายุ" และ "CVV" กรอกอะไรก็ได้ กด "ยืนยันบัตร" แล้วในฟอร์มขึ้น "บัตรผ่านการตรวจสอบ" และหน้าหลักขึ้น "ยืนยันบัตรแล้ว" ปุ่ม "ยืนยันคำสั่งซื้อ" จะกดได้เมื่อกรอกข้อมูลผู้รับครบ ติ๊กยอมรับเงื่อนไข และยืนยันบัตรแล้ว

**ใบเสร็จ (ข้อ 6)** ปุ่ม "ดาวน์โหลดใบเสร็จ" ในหน้า `/orders/DN-0001` เป็นลิงก์ไปไฟล์ `receipt-DN-0001.txt` บรรทัดแรกของไฟล์คือ `DN Shop - ใบเสร็จ` (วิธีรอและอ่านไฟล์ที่ดาวน์โหลดอยู่ในบท 27)

**ประวัติคำสั่งซื้อ (ข้อ 8 ถึง 9)** หน้า `/account` มี h2 "ประวัติคำสั่งซื้อ" ถ้ายังไม่เคยสั่งแสดง "ยังไม่มีคำสั่งซื้อ" ถ้าเคยแสดงรายการที่แต่ละบรรทัดเป็นลิงก์หมายเลขคำสั่งซื้อตามด้วยยอด เช่น `DN-0001 - 240 บาท`

## จุดที่มักพลาด

- **ไม่ลบ `dn_sid` ใน `auth.setup.ts`**: ทุก test ใช้ตะกร้าเดียวกัน ผลคือ test ที่รันขนานเห็นของและหมายเลขคำสั่งซื้อของกันและกัน
- **ใช้ `page.request` ผิดตัว**: ข้อมูลที่เตรียมต้องอยู่ใน session เดียวกับหน้าเว็บของ test นั้น ให้ใช้ `page.request` ไม่ใช่ context ใหม่ที่สร้างเอง
- **ไม่ตรวจ status ของ API ที่ใช้เตรียมข้อมูล**: ถ้า `POST /api/cart` ล้มโดยไม่มีใครเห็น test จะล้มที่ขั้นอื่นด้วยข้อความที่ไม่ช่วยหาต้นเหตุ
- **เปิด `/checkout` ทั้งที่ตะกร้าว่าง**: แอปส่งกลับ `/cart`
- **ลืมสร้างตัวรอ download ก่อนกดลิงก์**: ต้องเริ่มรอ event `download` ก่อนกด ไม่ใช่หลังกด
- **เขียน locator ซ้ำใน test**: ถ้าเห็นตัวเองเขียน `page.getByRole(...)` ในตัว test หลายที่ ให้ย้ายเข้า Page Object
- **ข้อ 7 ใช้ผลจากข้ออื่น**: test แต่ละข้อต้องรันเดี่ยวได้ ข้อ 7 ต้องเดินทั้งเส้นทางด้วยตัวเอง

## หน้าในแอปที่ใช้

**`/login`** ใช้ใน `auth.setup.ts` ปุ่ม "เข้าสู่ระบบ" กดได้เมื่อกรอกทั้งสองช่อง สำเร็จแล้วไป `/account`
**`/products`** ช่องค้นหา label "ค้นหาสินค้า" (กด Enter หรือปุ่ม "ค้นหา") รายการอยู่ใน `<ul aria-label="รายการสินค้า">` ข้อความ "พบสินค้า N รายการ" และปุ่ม "เพิ่มลงตะกร้า" ในแต่ละการ์ด หลังเพิ่มสำเร็จขึ้นข้อความสถานะ `เพิ่ม "{ชื่อสินค้า}" ลงตะกร้าแล้ว`
**`/cart`** รายการใน `<ul aria-label="สินค้าในตะกร้า">` ช่อง "โค้ดส่วนลด" ปุ่ม "ใช้โค้ด" และ `data-testid` ของ `subtotal`, `discount`, `total`
**`/checkout`** ข้อมูลผู้รับ วิธีส่ง วิธีชำระเงิน iframe ฟอร์มบัตร และ `data-testid="order-total"` (ยอดรวมค่าส่งแล้ว)
**`/orders/DN-0001`** heading "สั่งซื้อสำเร็จ" รายการสินค้า ยอดสุทธิ และลิงก์ "ดาวน์โหลดใบเสร็จ"
**`/account`** ข้อมูลบัญชี และ "ประวัติคำสั่งซื้อ" ผู้ใช้ตัวอย่าง `user@dnshop.test` รหัสผ่าน `password123` ชื่อ "สมชาย ใจดี"

## วิธีรันบทนี้

```bash
pnpm test --config lessons/55-capstone/playwright.config.ts
```

ก่อนเริ่มทำ ผลที่ควรได้คือ `10 skipped` (ทุกข้อและไฟล์ setup ยังเป็น `fixme`) เมื่อทำไปแล้วให้รันซ้ำเพื่อดูว่า test นิ่ง:

```bash
pnpm test --config lessons/55-capstone/playwright.config.ts --repeat-each=3
```

ดูทีละขั้นตอนด้วย UI mode:

```bash
pnpm test:ui --config lessons/55-capstone/playwright.config.ts
```

## แบบฝึกหัดในบทนี้

เปลี่ยน `test.fixme` เป็น `test` (และ `setup.fixme` เป็น `setup` ใน `auth.setup.ts`) แล้วเขียนตามแนวทางในคอมเมนต์ของแต่ละข้อ

1. ทุก test เริ่มด้วยสถานะที่ login แล้ว (เขียน `auth.setup.ts` และ test ตรวจเมนูหัวเว็บ)
2. ค้นหา "หนังสือ" แล้วพบ 2 รายการ
3. เพิ่มหนังสือสองเล่มจากหน้าสินค้า ตะกร้ายอดรวม 840 บาท
4. ใช้โค้ด DN10 (ตะกร้าเตรียมด้วย API)
5. จ่ายด้วยบัตรผ่าน iframe จนได้หน้าสั่งซื้อสำเร็จ
6. ดาวน์โหลดใบเสร็จ (คำสั่งซื้อเตรียมด้วย API)
7. เส้นทางเต็ม: ค้นหา เพิ่มสินค้า คูปอง ชำระเงินด้วยบัตร ใบเสร็จ และประวัติ ในหนึ่ง test
8. บัญชีที่ยังไม่เคยสั่งซื้อไม่มีประวัติ
9. คำสั่งซื้อที่สั่งแล้วขึ้นในประวัติของบัญชี

ทำเสร็จแล้วเปิดเฉลยของบทนี้บน branch `solutions` เทียบกับของคุณ จุดที่ควรดูคือการแบ่งหน้าที่ระหว่าง Page Object กับ fixture และเหตุผลในคอมเมนต์
