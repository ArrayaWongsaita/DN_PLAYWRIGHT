# บทที่ 22: test.step และสร้าง test จากข้อมูลหลายชุด 🏫

บทนี้เขียนให้อ่านเองได้ ตัวอย่างทุกอันรันได้จริง ลองรันแล้วแก้ค่าเล่นดูระหว่างอ่าน

## จบบทนี้แล้วทำอะไรได้

- แบ่ง test ยาวๆ เป็นขั้นตอนที่มีชื่อด้วย `test.step` (และซ้อน step ได้)
- วน `for...of` สร้าง test หลายตัวจาก array ของข้อมูล (parameterized test)
- ตั้งชื่อ test ที่สร้างจากข้อมูลให้ไม่ซ้ำและอ่านง่าย
- รู้ว่า test ควรแยกเป็นหลายตัวหรือแบ่งเป็น step เมื่อไหร่

## เชื่อมกับที่รู้แล้ว

Jest มี `test.each` (หรือ `it.each`) สำหรับรัน test เดิมกับข้อมูลหลายชุด Playwright ไม่มี `test.each` แต่ใช้ลูปธรรมดาของ JavaScript/TypeScript สร้าง test ได้เลย เพราะไฟล์ test ถูกรันเป็นโค้ดปกติเพื่อ "ลงทะเบียน" test ก่อน ส่วน `test.step` ไม่มีใน Jest ใกล้เคียงที่สุดคือการคอมเมนต์แบ่งช่วงในตัว test แต่ใน Playwright ชื่อ step ปรากฏในรายงานจริง

## เนื้อหา

### 1. test.step: ตั้งชื่อขั้นตอน

```ts
test("ซื้อเสื้อยืดแล้วใช้โค้ด DN10 ได้ราคา 261 บาท", async ({ page }) => {
  await test.step("เพิ่มเสื้อยืดลงตะกร้า", async () => {
    await page.goto("/products/p04");
    await page.getByRole("button", { name: "เพิ่มลงตะกร้า" }).click();
  });

  await test.step("ใช้โค้ดส่วนลด", async () => {
    // ...
  });
});
```

- รับ **ชื่อ** กับ **ฟังก์ชัน async** ต้อง `await` ทั้งตัว `test.step(...)` และคำสั่งข้างใน
- ชื่อ step ปรากฏใน HTML report, trace viewer (บท 14) และ error message ตอน fail: จะเห็นเช่น `ใช้โค้ดส่วนลด › ตรวจข้อความสำเร็จ` ทำให้รู้ทันทีว่าพังที่ขั้นตอนไหน แทนที่จะต้องไล่ดูบรรทัดโค้ด
- ตัวแปรที่ประกาศใน step ใช้ได้เฉพาะภายใน step ถ้าต้องการส่งค่าออก ให้ `return` จากฟังก์ชัน (`const price = await test.step("อ่านราคา", async () => { return ... })`) หรือประกาศตัวแปรไว้นอก step
- ถ้ามี `expect` fail ใน step test ทั้งตัวก็ fail เหมือนเดิม step ไม่ได้เป็น test ย่อยที่แยกผลกัน

### 2. step ซ้อนกัน

```ts
await test.step("ใช้โค้ดส่วนลด", async () => {
  await page.goto("/cart");
  await test.step("กรอกโค้ด DN10", async () => { /* ... */ });
  await test.step("ตรวจข้อความสำเร็จ", async () => { /* ... */ });
});
```

step ซ้อนใน step ได้หลายชั้น report จะแสดงเป็นลำดับชั้น ใช้ชั้นนอกเป็น "เป้าหมายใหญ่" ชั้นในเป็นการกระทำย่อย แต่ซ้อนไม่เกิน 2 ชั้นก็พอ ลึกกว่านั้นอ่านยาก

เกร็ด: `test.step(name, fn, { box: true })` ทำให้ step ถูกนับเป็นกล่องทึบ: ถ้า error เกิดข้างใน report จะชี้ที่บรรทัดที่เรียก step แทนบรรทัดข้างใน เหมาะกับ helper ที่ใช้ซ้ำหลายที่ (ไม่ต้องใช้ในบทนี้)

#### step กับการแยกเป็นหลาย test

| | `test.step` | หลาย `test` |
|---|---|---|
| ผลผ่าน/ไม่ผ่าน | รวมเป็นผลเดียว | แยกกันต่อ test |
| state (หน้า, ตะกร้า) | ต่อเนื่อง | แต่ละตัวเริ่มใหม่ (บท 20) |
| ใช้เมื่อ | flow เดียวที่ขั้นตอนต่อกัน เช่นเลือกสินค้า → ตะกร้า → ชำระเงิน | พฤติกรรมที่แยกจากกันได้ |

อย่าใช้ step เพื่อยัดหลายเรื่องไม่เกี่ยวกันไว้ใน test เดียว

### 3. สร้าง test จากข้อมูลด้วยลูป

```ts
const searchCases = [
  { q: "หนังสือ", expected: 2 },
  { q: "DN", expected: 2 },
  { q: "ไม่มีสินค้านี้", expected: 0 },
];

for (const { q, expected } of searchCases) {
  test(`ค้นหา "${q}" ได้ ${expected} รายการ`, async ({ page }) => {
    await page.goto("/products");
    await expect(page.getByText("พบสินค้า 10 รายการ")).toBeVisible();
    await page.getByLabel("ค้นหาสินค้า").fill(q);
    await page.getByLabel("ค้นหาสินค้า").press("Enter");
    await expect(page.getByText(`พบสินค้า ${expected} รายการ`)).toBeVisible();
  });
}
```

ผลคือ 3 test แยกกัน ชื่อใน report ต่างกันตามข้อมูล แต่ละตัวเปิดหน้าใหม่ของตัวเอง ล้มเหลวแยกกัน และรันขนานกันได้ ข้อดีเทียบกับวนในตัว test เดียว: ถ้ากรณีที่ 2 fail กรณีที่ 3 ยังถูกรัน (วนใน test เดียว fail แล้วหยุดทั้งหมด)

#### รายละเอียดที่ต้องระวัง

- **ชื่อต้องไม่ซ้ำ**: test สองตัวชื่อเดียวกันในไฟล์เดียวกันทำให้ Playwright error (`duplicate test title`) ใส่ค่าจากข้อมูลเข้าไปในชื่อเสมอ
- **ลูปทำงานตอน "โหลดไฟล์"** ไม่ใช่ตอน test รัน อย่าใส่ `await` หรือใช้ `page` นอก `test(...)`
- **ตัวแปรลูป**: ใช้ `const` ในหัว `for...of` ทำให้แต่ละรอบมีตัวแปรของตัวเอง (ถ้าใช้ `var` จะผิด)
- **ข้อมูลเก็บไว้ด้านบนไฟล์** เป็น array ธรรมดา แก้หรือเพิ่มชุดได้ง่าย ไม่ต้องแตะโค้ด test
- **ทำไมต้อง `พบสินค้า 10 รายการ` ก่อนพิมพ์ค้นหา**: ถ้าไม่รอ ข้อความ "พบสินค้า N รายการ" ของรอบก่อนหน้า (ระหว่างค้นหา) อาจยังค้างบนหน้า ทำให้อ่านค่าผิดหรือ assertion ผ่านเร็วเกินจริง รอให้หน้าอยู่ในสภาพตั้งต้นที่รู้ค่าก่อน แล้วค่อยเปลี่ยน ตอนเปลี่ยนค่าที่คาดหวังใน `expect` จะรอจนเปลี่ยนเป็นค่านั้นเอง
- **อย่าให้ test ที่สร้างจากลูปมากเกินจำเป็น**: 3–5 ชุดที่ครอบคลุมกรณีที่ต่างกันจริง (มีผล, ไม่มีผล, เป็นกรณีพิเศษ) ดีกว่า 50 ชุดที่ซ้ำกัน

## จุดที่มักพลาด

- **ลืม `await` หน้า `test.step`**: ขั้นตอนไม่ถูกรอ ทำให้ test เดินต่อก่อนจบและ report แสดงผิด (บท 03)
- **ตั้งชื่อ test ในลูปเหมือนกัน**: error `duplicate test title` ให้ใส่ค่าจากข้อมูลในชื่อ
- **ซ้อน step ลึกเกินไป**: report อ่านยาก
- **คิดว่า step ที่ fail แล้ว test ยังเดินต่อ**: ไม่เดินต่อ (`expect` ปกติ fail แล้วหยุด test)

## วิธีรันบทนี้

```bash
pnpm test 22-steps-parameterize
```

ผลที่ควรได้ก่อนเริ่มทำแบบฝึกหัด: `4 passed` และ `3 skipped` เปิด `pnpm report` แล้วดูว่า step ซ้อนกันแสดงเป็นอย่างไร
